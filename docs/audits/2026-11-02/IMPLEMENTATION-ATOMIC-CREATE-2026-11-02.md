# 새 아기 원자적 등록 — 서버 경로와 클라이언트 준비

작업일: 2026-11-02 (Asia/Seoul)

## 구현

- `sql/008_atomic_create_backup.sql`: 로그인 JWT의 auth.uid()를 소유자로 사용한다. 클라이언트는 소유자 ID·이메일·기기 ID·초대코드로 소유권을 지정할 수 없다.
- 아기, owner membership, revision 0 스냅샷, 재시도 영수증을 하나의 DB 호출로 만든다. 마지막 단계가 실패하면 앞선 삽입도 롤백된다. 빈 기록 목록으로 새 아기를 등록하는 것도 허용한다.
- 계정별 request_id와 baby_id·원본 payload를 대조한다. 동일 재시도는 중복 생성하지 않으며, 요청 ID를 다른 내용에 재사용하면 거부한다. 이미 사용 중인 아기를 새로 소유하는 기능은 제공하지 않는다.
- 재시도가 나중의 수정 기록을 초기 버전으로 덮어쓰지 않는다. 소유권이 철회된 뒤 같은 요청을 재실행해도 권한을 되살리지 않는다.
- 생성 영수증에는 현재 버전을 담지 않는다. 최초 등록 성공/재시도 후에는 최신 스냅샷을 별도로 읽고 수락해야 한다. 영수증만 보고 버전 0으로 덮어쓰면 안 된다.
- `createAtomicBackup()`은 지원 데이터만 전송하고 영수증을 검사한다. 원자적 백업 모듈은 앱 로그인과 같은 SSR 브라우저 클라이언트를 사용하도록 정리했다.
- 레거시 초대 참여용 코드가 아닌 PRIVATE- 접두사의 내부 고유 값을 사용한다. 가족 초대는 이후 새 권한 기반 흐름으로 별도 구현한다.

## 검증

가상 DB(PGlite) 신규 등록 13개, 클라이언트 모의 RPC 7개, 기존 원자적 DB 22개, 기존 클라이언트 10개, 공유 중지 10개를 검증했다. TypeScript와 변경 클라이언트 ESLint도 통과했다. 실제 JWT·다중 DB 세션 경합·운영 적용 검증은 아니다.

## 적용 상태와 다음 순서

008은 운영에 실행하지 않았다. 004/005/007이 준비된 검증 환경에서 적용할 후속 SQL이다. 기존 데이터·권한은 변경하지 않았으며 클라우드 중지 상태와 로컬 등록 UI를 유지한다. 커밋·푸시·배포하지 않았다.

1. 검증 환경에서 007 → 008 순서로 적용하고 실제 로그인 계정의 허용/거부·동시 재시도를 검증한다.
2. 앱의 새 등록/로컬 기록 연결 흐름에 안정적인 baby UUID·request UUID·동일 재시도 payload 보관을 추가한다. 요청 결과가 불확실하면 새 ID로 다시 만들지 않는다.
3. 생성 후 현재 스냅샷을 읽고 수락한 버전과 로컬 대상/계정을 함께 보관한다. 세션·아기·로컬 기록이 바뀐 응답은 연결에 반영하지 않는다.
4. 생성·공유·조회·복원·자동 백업·관리자 경로를 함께 전환하고 기존 delete→insert 경로를 제거한다. 그 전에는 중지 정책을 해제하지 않는다.

새 request 테이블도 아기 삭제를 RESTRICT한다. 계정 탈퇴는 request 행을 CASCADE 제거하지만 이것이 아기·스냅샷의 파기를 뜻하지 않는다. 이후 아기/계정 삭제 기능에서 소유권과 파기 범위를 명시적으로 처리해야 한다. 과거 25개 테스트 아기는 재생성·이관하지 않았다.
