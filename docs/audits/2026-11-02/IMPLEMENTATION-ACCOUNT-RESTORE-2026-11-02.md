# 계정별 백업 목록·새 기기 복원

작성: 2026-11-02 (Asia/Seoul)

## 구현 결과

설정 → 가족과 첫 실행 화면에 '다른 기기의 기록 가져오기'를 연결했다. 로그인한 계정이 접근 가능한 아기만 목록으로 확인하고, 프로필·성장·접종 건수를 본 뒤 명시적으로 복원한다. 기존 아기를 교체하지 않고 새 로컬 아기로 추가하므로 기존 사진·메모·관찰과 아기별 기록을 보존한다.

- `sql/010_list_account_backups.sql`: 예상 계정과 JWT를 대조하고 membership으로 제한한다. 공개 레거시 프로필이 아니라 canonical snapshot에서 이름·생일·성별·역할·버전을 읽는다. UUID 기반 20건 페이지와 다음 커서를 제공한다. 초기 스냅샷이 없는 아기는 목록에 넣지 않는다.
- 목록의 역할·날짜·버전·UUID 순서·커서를 검증한다. 조회 실패를 빈 목록으로 처리하지 않는다. 선택 후 전체 스냅샷은 기존 검증 클라이언트로 읽는다.
- 확인 중 계정·메모리/디스크의 기기 기록이 달라지면 중단한다. 복원 직전에 서버를 다시 읽어 버전·내용이 미리보기와 동일한지도 확인한다. 이미 이 기기에 연결·등록 대기 중인 실제 아기는 중복 추가하지 않는다. 로컬 프로필이 사라진 오래된 연결은 복원을 막지 않는다.
- 성장 기록의 서버 ID를 유지하고 새 localBabyId로 구분한다. 이전 레거시 기록의 소유자와 사진·메모는 보존하며, 새 기기의 소유자 없는 기록을 복원 아기에게 임의 배정하지 않는다.
- 복원 연결에는 실제 읽은 snapshot·revision·역할을 함께 저장한다. 자동 백업은 항상 꺼짐으로 시작한다. reader는 읽기 전용 안내를 표시하고 자동 전송을 허용하지 않는다.
- 복원은 서버에 생성/갱신 요청을 보내지 않는다. 사진·메모·발달 관찰은 현재 서버 백업에 포함되지 않아 내려받지 않는다.

## 기기 저장 중단 처리

프로필·성장·접종·연결 저장은 localStorage의 여러 키에 걸친다. 단일 DB 트랜잭션처럼 가정하지 않고 이전/다음 값을 담은 write-ahead journal을 먼저 보관하고 각 쓰기를 검증한다. 중간 실패 시 기존 값으로 복구한다. 다음 문서는 prepared 저널이면 이전 값으로, committed 저널이면 새 값으로 복구한 뒤 관련 Zustand 저장소를 읽는다.

복원 완료 후 전체 화면 이동으로 네 저장소를 함께 다시 읽는다. 완료 전후 온라인 작업은 중단한다. 복구 자체가 실패하거나 저널이 잘못됐으면 기록 변경/온라인 전송 대신 상태 확인 화면과 재시도 버튼을 제공한다. 브라우저 데이터를 지우도록 안내하지 않는다.

저널은 같은 브라우저 안에만 보관하며 서버로 보내지 않는다. 기존 사진 등으로 저장 공간이 부족하면 복원을 실패 처리할 수 있다. 이 구현이 브라우저의 다중 탭 동시 쓰기 전체를 원자적으로 잠근다는 뜻은 아니다. 실제 다중 탭·실기기·저장소 손상 복구 검증은 남아 있다.

## 공개 상태와 다음 단계

새 등록과 같은 NEXT_PUBLIC_ATOMIC_REGISTRATION_ENABLED=true인 검증 환경 전용이다. 010은 007 이후 적용하는 SQL이며, 앱 전체 검증에는 007 → 008 → 009 → 010을 사용한다. 운영 SQL/환경/데이터는 변경하지 않았다. 레거시 클라우드 중지 상태를 유지하며 커밋·푸시·배포하지 않았다.

다음 작업은 새 연결 해제·아기/계정 삭제와 가족 권한 경로의 전환이다. 기존 로컬 아기와의 항목별 병합·기존 대상 교체는 이번에 제공하지 않는다. 실제 JWT·다중 DB 세션·실기기 검증과 운영 적용도 남아 있다.
