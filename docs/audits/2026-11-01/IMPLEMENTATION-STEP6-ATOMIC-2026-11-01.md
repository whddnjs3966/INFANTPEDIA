# STEP 6 4차 — 원자적 저장 프로토콜 준비 및 로컬 검증

날짜: 2026-11-01 (Asia/Seoul)

## 완료 범위

- 별도 가족 권한 테이블과 버전이 있는 전체 스냅샷 테이블을 만드는 SQL 변경안 작성.
- 명시적으로 검증한 owner/editor만 쓰고 reader는 읽기만 하는 읽기/쓰기 RPC 구현. 기존 creator/device 값으로 새 권한을 자동 부여하지 않음.
- 프로필·성장·접종을 한 행으로 저장하여 마지막 단계의 DB 오류에서도 데이터와 버전 전체 롤백.
- 행 잠금과 기준 버전 비교로 오래된 버전 덮어쓰기 차단, 동일 요청의 마지막 성공 확인 재시도 지원.
- 잘못된 값·날짜·중복 기록·다른 아기 데이터 차단. 직접 테이블 쓰기로 버전 검사를 우회하지 못하게 제한.
- 레거시 아기 삭제가 새 백업을 연쇄 삭제하지 않도록 외래키 RESTRICT 적용.
- 별도 TypeScript 클라이언트 모듈에서 입력·응답·버전·요청 ID 검증, 충돌/권한/준비 안 됨/통신 오류 구분. 구형 삭제/삽입 fallback 없음.
- 전환 전 소유권 확인·초기 데이터 이관·전체 호출 경로 교체 절차를 `docs/atomic-backup-cutover.md`에 정리.

## 검증

| 검사 | 결과 |
|---|---|
| `npm run check:atomic-db` | 실제 SQL을 로컬 PGlite에서 실행한 22개 검사 통과 |
| `npm run check:atomic-client` | 모의 RPC 기반 클라이언트 검사 10개 통과 |
| ESLint·TypeScript | 새 모듈 검사 통과 |
| `npm run build -- --webpack` | 최종 프로덕션 빌드 통과 |

DB 검사는 인증 없는 접근·권한 없는 접근·읽기 전용 계정·업데이트·버전 충돌·요청 재사용·실패 롤백·직접 쓰기 차단·레거시 연쇄 삭제 차단·권한 철회를 포함한다. 클라이언트 검사는 알려지지 않은 버전, 불일치 응답, RPC 부재, 불확실한 네트워크 재시도와 구형 fallback 차단을 포함한다.

테스트 의존성은 devDependency `@electric-sql/pglite@0.5.14`로 고정했다. 가상 인증 사용자와 메모리 DB만 사용했으며 운영 DB에는 연결/적용하지 않았다. 단일 연결에서 같은 기준 버전의 두 요청 중 하나가 충돌하는 동작을 확인했으며 실제 다중 DB 세션 동시성 스트레스 검사는 아니다.

## 현재 앱과의 관계 — 중요

**SQL은 운영 미적용, 새 클라이언트 모듈은 현재 SyncManager에 미연결이다.** 현재 앱의 기존 delete→insert 경로가 이번에 교체됐다는 의미가 아니다. 새 스냅샷과 레거시 기록도 자동 동기화되지 않는다.

기존 Supabase 주소는 직전 검증에서 DNS ENOTFOUND였으며 프로젝트 상태/변경 URL을 사용자에게 질문했다. 응답이나 연결 확인 없이 운영 설정을 변경하지 않았다. 신뢰할 수 있는 가족 권한·기준 스냅샷이 없는 경우 새 경로가 동작하도록 자동 초기화하지 않는다.

다음 적용 단계는 연결 확인 → 스테이징 DB 적용 → 검증된 소유권/기준 데이터 이관 → 생성/참여/복원/전송의 전체 경로 전환 → 실제 로그인·다중 기기 검증이다. 새 기기 복원·실제 서비스 동기화·기존 RLS·서버 파기 문제는 여전히 미완료다.
