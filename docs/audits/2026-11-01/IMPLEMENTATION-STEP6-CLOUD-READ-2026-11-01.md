# STEP 6 3차 — 공유 기록 가져오기 전 검증

날짜: 2026-11-01 (Asia/Seoul)

## 먼저 해결한 문제

기존 join/pull 경로가 성장·접종 조회 오류를 빈 배열로 바꿔 반환해, 호출부에서 기기 기록을 빈 서버 기록으로 교체할 수 있었다. 이번에는 복원 전 조회 검증과 로컬 대상 보호부터 보완했다. **서버 원자적 갱신·동시 수정 보호를 구현한 것은 아니다.**

## 반영

- 프로필과 성장·접종 목록이 모두 성공해야 데이터를 반환한다. 배열 누락, 오류, exact count와 반환 길이 불일치를 거부해 제한에 의해 잘린 목록을 그대로 가져오지 않는다.
- 다른 아기의 행, 잘못된 날짜/수치, 중복 측정 ID·접종 차수, 알 수 없는 백신 차수, 잘못된 프로필을 검증한다. 측정 월령은 측정일 기준으로 다시 계산한다.
- 서버 측정 ID를 유지하고, 기존 아기에 가져올 때 로컬 아기 ID와 조합해 안정적으로 저장한다. 접종은 토글을 반복하는 대신 검증된 목록을 교체해 중복 취소를 피한다.
- 조회 시작과 완료 시 로그인 계정을 확인한다. 비로그인은 공유 조회·기기 등록으로 진행하지 않는다. 첫 실행의 초대코드 화면에 로그인 링크를 추가했다.
- 공유 기기 등록 실패도 가져오기 실패로 처리한다.
- 가져오는 동안 현재 아기·프로필·성장/접종 기록·공유 매핑이 바뀌면 원래 기기 데이터를 교체하지 않는다.
- 해당 종류의 기기 기록이 있는데 서버가 빈 목록이면 교체를 중단하고 대상·조회 권한 확인을 안내한다. 실제 빈 서버로 기기 기록을 비우는 가져오기도 이 보호 조건에서는 허용하지 않는다.
- 공유 연결 유무와 관계없이 교체 확인을 먼저 표시한다. 현재 아기 대상과 사진·발달 관찰 보존, 측정 메모를 가져오지 못할 수 있음을 안내한다.

## 검증

- `npm run check:cloud-read`: 실제 TS 서비스·검증기·기기 저장소를 모의 DB/인증 및 메모리로 실행한 17개 회귀 검사 통과.
- `npm run check:backup`: 기존 전송 상태 회귀 16개 통과.
- 변경 파일 ESLint 오류/경고 0, TypeScript 포함 최종 Webpack 프로덕션 빌드 통과, 공백 오류 없음.
- 브라우저에서 가족 공유의 기기 기록 보호 안내와 첫 실행 초대코드의 로그인 링크 표시 확인. 로그인·초대 연결·기록 교체는 실행하지 않았다.
- QA 프록시 쓰기 요청 0건. 운영 사용자 데이터 조회·변경 없이 테스트했다.
- 설정된 Supabase 주소 DNS를 다시 검사했으며 `ENOTFOUND`. 실제 서버 연동은 검증하지 못했다.

## 남은 범위

1. 실제 Supabase 연결 복구 및 인증·가족 membership/RLS 검증.
2. 원자적 저장 API와 버전 기반 동시 수정 충돌 처리. 기존 delete→insert 업로드 방식은 아직 남아 있다.
3. 일관된 서버 스냅샷 읽기와 페이지 단위 조회. 현재는 잘린 응답을 안전하게 거부하며, 서버의 동시 변경이나 RLS에 의해 숨겨진 행을 클라이언트만으로 증명하지 못한다.
4. 로그인 후 아기 목록 조회·새 기기 복원·병합 정책과 실서비스 검증. 현재 pullFromCloud는 호출 UI에 자동 연결하지 않았다.
5. 여러 로컬 저장소 적용 중 저장 용량 오류의 원자성·복구 처리. 이번 가드는 조회 실패 및 적용 전 대상 변경 보호이며 모든 저장 실패의 트랜잭션 보장은 아니다.
