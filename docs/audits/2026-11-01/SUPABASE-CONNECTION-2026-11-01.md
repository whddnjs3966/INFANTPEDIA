# 기존 Supabase 프로젝트 연결 재확인

날짜: 2026-11-01 (Asia/Seoul)

사용자가 기존 프로젝트를 계속 사용한다고 확인했다. 환경변수나 프로젝트 주소를 변경하지 않고 읽기 전용으로 재검사했다.

| 확인 | 결과 |
|---|---|
| `.env.local`의 호스트와 기존 Auth 설정 문서 | 일치 |
| 프로젝트 DNS | resolved |
| 비교용 supabase.com / example.com DNS | 모두 resolved |
| 인증 `/auth/v1/health` | HTTP 200 |
| 공개 콘텐츠 `months_info`의 month 한 건 GET | HTTP 200 |
| 신규 `backup_snapshots` 메타데이터 HEAD, limit=0 | HTTP 404 |

이전 ENOTFOUND는 당시 관찰 기록으로 유지한다. 이번 재검사에서는 통신이 회복됐지만, 원인이 프로젝트 중지·일시 DNS 장애 중 무엇이었는지는 확인하지 않았다. 기존 주소를 계속 사용한다.

404는 신규 테이블이 현재 REST API에 노출되어 있지 않다는 결과다. 이 검사만으로 실제 DB 객체 존재 여부나 모든 권한을 판정하지 않는다. 이번에 작성한 `007_atomic_backup.sql`을 운영에 실행하지 않았으며, 새 RPC를 현재 앱 경로에 연결하지도 않았다.

프로젝트 통신 복구는 로그인 완료·가족 권한·운영 DB 정책·실제 백업/복원의 검증 완료를 뜻하지 않는다. 새 경로 적용 전 검증된 소유권과 스테이징/이관·전체 호출 경로 전환이 필요하다. 세부 절차는 `docs/atomic-backup-cutover.md`를 따른다.

API 키 값·사용자 기록을 출력하지 않았고, 개인정보 테이블의 행이나 실제 가족 기록을 조회하지 않았다. 운영 데이터 생성·수정·삭제, DB 마이그레이션·푸시·배포는 하지 않았다.
