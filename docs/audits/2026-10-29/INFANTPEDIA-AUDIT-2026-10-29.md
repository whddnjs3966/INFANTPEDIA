## 1. 현재 상태와 판단

**기능과 화면의 기반은 상당히 갖춰져 있습니다. 개발 재개 시 첫 작업은 데이터 분리·인증·동기화 안정화가 적절합니다.**

모바일 육아 백과와 성장 기록 앱으로서 홈, 백과, 성장, 꿀팁, 설정의 5개 탭이 구현돼 있습니다. 백과 안에는 8개 메뉴가 있고, 건강 FAQ 89개·발달 체크 169개·육아 팁 40개 등 정적 콘텐츠도 있습니다. 청록색, 둥근 카드, 하단 내비게이션을 사용하는 디자인은 대체로 일관됩니다.

프로덕션 빌드와 TypeScript 검사는 통과했습니다. 그러나 A 아기의 측정값이 B 아기의 성장 화면에 표시되는 결함을 실제 화면에서 재현했습니다. 관리자 인증, 가족 공유 권한, 자동 클라우드 업로드, 날짜 계산, 의료 콘텐츠에도 공개 전 해결해야 할 문제가 있습니다. **현재 상태에서 실사용자 데이터를 추가로 받거나 공개 범위를 넓히는 것은 권장하지 않습니다.**

이 문서는 분석 결과입니다. 앱 기능·디자인 수정은 수행하지 않았습니다. 기존 개발자의 수정 파일은 보존했습니다.

## 2. 분석 범위와 검증 방식

### 확인한 범위

- `src/app`의 사용자 화면·관리자 화면·API, 공통 레이아웃과 내비게이션.
- Zustand 저장소, Supabase 클라이언트, 동기화 서비스, 공유 흐름.
- SQL 스키마·초기 콘텐츠·RLS 정책, PWA manifest와 service worker.
- PRD, 로드맵, 실행 설정과 관련 문서.
- 프로덕션 빌드, TypeScript, 린트 명령, 로컬 HTTP 검사, 메모리 기반 경계 검사.
- 로컬 브라우저의 가상 아기 등록·측정·아기 전환·백과·FAQ 검색·식단·통합검색·테마 전환.

### 운영 데이터 보호

- 프로덕션 실행: `127.0.0.1:3217`, 빌드 및 로컬 HTTP 검사에 사용.
- 화면 QA: `127.0.0.1:3219`, Supabase 주소를 로컬 QA 프록시 `127.0.0.1:3218`로 교체.
- QA 프록시는 공개 콘텐츠 4개 테이블의 GET만 원래 서버로 전달했습니다. 공유·측정·접종 쓰기는 전부 로컬 메모리에서 처리했습니다.
- 등록한 아기와 측정값은 가상 데이터입니다. 실제 사용자 데이터 조회·수정·삭제, 배포, GitHub push는 수행하지 않았습니다.
- QA 프록시는 실제 Supabase RLS를 재현하는 서버가 아닙니다. 이를 통과했다는 이유로 실제 클라우드 공유가 정상이라고 판정하지 않았습니다.

### 결과를 읽는 기준

| 표시 | 의미 |
|---|---|
| 실행 재현 | 로컬 앱·브라우저·HTTP 요청에서 직접 확인 |
| 메모리 재현 | 실제 저장소 코드를 불러와 가상 데이터와 제어한 날짜로 검증 |
| 코드 확인 | 호출 경로·SQL·구현에서 확인, 실제 운영 환경 적용 여부는 별도 |
| 확인 보류 | 외부 서비스·계정·실기기가 필요하여 완료로 판정하지 않은 항목 |

현재 로컬 환경에 설정된 Supabase 호스트는 DNS 조회에서 `ENOTFOUND`를 반환했습니다. 프로젝트 중지·삭제·주소 변경·로컬 DNS 문제 중 어느 원인인지는 확인하지 못했습니다. 따라서 운영 DB의 실제 정책, 저장된 콘텐츠, 소셜 로그인 완료, 두 기기 간 동기화는 검증 완료 항목에 포함하지 않습니다.

### 구현돼 있으나 화면/흐름에 연결되지 않은 부분

- `GrowthAlertCard`: 성장 알림 컴포넌트가 있지만 실제 페이지의 호출이 없습니다.
- `InstallPrompt`: 설치 유도 컴포넌트가 있지만 실제 레이아웃의 호출이 없습니다. 브라우저 자체 설치 기능과는 별개입니다.
- `pullFromCloud`: 정의돼 있지만 호출부가 없어 로그인 후 기존 클라우드 기록을 자동 복원하는 흐름이 완성되지 않았습니다.
- `updateMeasurement`: 저장소의 수정 함수는 있지만 기록 수정 화면에서 사용되지 않습니다.
- `shared_daily_logs`: SQL·관리자 통계의 일지 관련 흔적입니다. 현재 사용자용 수유/수면 일지 기능으로 보기는 어렵습니다.

### 아직 사용자 기능으로 구현되지 않은 확장 항목

성장 보고서 PDF, CSV/JSON 내보내기·가져오기, 푸시 알림, 실시간 양방향 동기화·오프라인 쓰기 큐, 사용자 작성 레시피 DB, 전문가 Q&A/커뮤니티, 다국어 기능은 현재 사용 가능한 기능으로 확인되지 않았습니다.

### 5.2 자동 업로드와 공유 흐름 — SYN-01~04

`SyncManager`는 로그인 여부 대신 프로필 존재만 확인하고 3초 뒤 `shareBaby` 또는 `pushToCloud`를 호출합니다. 테스트에서 비로그인 A와 B 각각의 공유 생성 요청이 로컬 가상 서버에 기록됐습니다. B의 클라우드 ID에도 A의 키 58.4가 업로드되었습니다. 세부 기록은 `mock-sync-events.json`에 있습니다.

개인정보 안내는 비로그인 정보를 localStorage에만 보관한다고 설명합니다. 현재 코드 동작과 일치하지 않습니다. 이 환경에서는 원래 서버가 DNS 조회에 실패했기 때문에 실제 업로드 성공으로 단정할 수 없으며, 가상 서버에서 업로드 시도 경로를 확인한 것입니다.

공유 참여의 `clearAll()`은 현재 아기 외의 기록까지 지웁니다. 연결 해제는 로컬 mapping만 제거하므로 자동 동기화가 새 공유를 생성할 수 있습니다. 또한 `pushToCloud`는 클라우드 기록을 전부 삭제한 뒤 다시 넣고, 삭제 에러를 검사하지 않습니다. 측정 ID와 메모도 보존하지 않습니다. 두 보호자가 함께 수정하거나 중간에 통신이 끊길 때 기록 보존을 보장하기 어렵습니다.

### 5.3 관리자 인증과 공유 권한 — SEC-01~03

관리자 로그인에는 코드에 고정된 자격정보가 있습니다. 서명 키가 환경변수에 없으면 공개 코드의 기본값을 사용합니다. 원격 관리자 API가 아기 기록 조회·수정·삭제까지 제공하므로 우선 수정이 필요합니다. 이 보고서에는 자격정보와 서명 키 값을 재기재하지 않았습니다.

로컬 `/api/admin/session`에 **2000년 시각의 유효 서명 토큰**을 전달했을 때 401 대신 200이 반환됐습니다. 서명 생성은 로컬 설정을 사용했으며 운영 관리자 데이터는 조회하지 않았습니다. 쿠키 보관기간 설정은 이미 발급된 토큰의 서버 만료 검증을 대신하지 못합니다.

### 후속 검증이 필요한 항목

- Supabase 프로젝트 복구/설정 확인 후 실제 테이블·RLS·마이그레이션 상태 검증.

### 재실행 자료

- `code-checks.cjs` / `code-checks.json`: 실제 저장소 코드를 사용한 메모리 재현과 콘텐츠 수량. localStorage 영속성 대신 메모리를 사용하므로 CLI의 storage 경고는 브라우저 저장 실패 판정이 아닙니다.
- `http-checks.cjs` / `http-checks.json`: 로컬 프로덕션 서버 경로·세션·manifest 검사. 세션 검사 결과 파일에는 비밀값이나 토큰을 저장하지 않습니다.
- `qa-proxy.cjs`: 공개 콘텐츠 GET만 전달하고 공유 쓰기는 로컬 메모리에서 처리하는 격리 서버.
- `mock-sync-events.json`: 가상 아기 A/B에 대한 로컬 쓰기 요청 증거.
- 스크립트의 원본 코드 경로는 현재 PC의 `D:/workplace/03-INFANTPEDIA`입니다. 다른 환경에서는 해당 경로를 먼저 조정해야 합니다.

## 8. 개선 작업의 권장 순서

### 1단계 — 데이터와 접근 통제

1. 현재 Supabase 프로젝트 상태·환경변수·DB 정책을 확인하고 안전한 테스트 프로젝트를 마련합니다.
2. 관리자 고정 인증/기본 서명키를 없애고 관리자 역할과 서버 세션 검사를 구현합니다.
3. 가족/아기/보호자 관계를 명시한 스키마와 RLS를 설계합니다.
4. 로컬 모드와 클라우드 모드, 공유 참여·탈퇴·파기 범위를 확정합니다.
5. 위험한 수면 문구와 서로 다른 발열 기준을 우선 교정하고 의료 검수 목록을 만듭니다.

완료 기준: 다른 계정/가족 접근이 거절되고 비로그인 데이터 보관 안내와 실제 동작이 일치해야 합니다.

### 2단계 — 핵심 기록의 신뢰성

1. 모든 기록에 babyId를 필수화하고 기존 데이터 마이그레이션을 구현합니다.
2. 홈/성장/접종/발달/공유가 같은 아기별 데이터 조회 함수를 사용하게 정리합니다.
3. 일수·개월·기본 날짜를 공통 한국 시간 유틸로 통합합니다.
4. delete+insert 동기화를 안정적인 레코드 ID·트랜잭션·재시도·충돌 처리로 교체합니다.
5. 로그인 복원, 공유 참여 병합, 연결 해제, 측정 메모·수정 흐름을 완성합니다.

완료 기준: 두 아기·두 보호자·두 기기 시나리오에서 기록 혼합·유실·되돌아감이 없어야 합니다.

### 3단계 — 읽기와 탐색 경험

1. DB 타입/단위를 맞추고 오류·빈 상태·오프라인을 구분합니다.
2. 본문 크기·대비·터치 영역·모달·확대·스크린리더 이름을 보완합니다.
3. 백과 하위 메뉴와 월령을 URL에 반영하고 홈 바로가기를 해당 상세에 연결합니다.
4. FAQ·가이드를 포함한 검색과 원문 이동을 구현합니다.
5. 현재 아기 전환·마지막 저장/동기화 시각을 주요 화면에 명확하게 표시합니다.

### 4단계 — 재발 방지와 기능 확장

1. ESLint 명령/설정과 CI를 복구하고 날짜·아기 분리·동기화·권한 회귀검사를 추가합니다.
2. 실제 기기 PWA·오프라인·업데이트와 로그아웃 캐시 처리를 점검합니다.
3. 오류 수집과 최소한의 성능 관찰을 연결합니다.
4. 안정화 후 JSON/CSV 백업·성장 PDF·예방접종 알림을 검토합니다.
5. 레시피 DB/전문가 Q&A 등 콘텐츠 확장은 검수와 운영 체계를 갖춘 뒤 추진합니다.
