# 원자적 백업 전환 절차 — 운영 미적용

최신 상태(2026-11-04): 007~011을 격리된 실제 로컬 PostgreSQL에서 적용하고 백업/복원·가족 권한·파기·병합·다중 세션을 검사했다. 로컬 서명 JWT 게이트웨이는 Supabase Auth가 아니며 운영 중지는 유지한다. 실제 Supabase 플랫폼과 실기기 최종 검증·관리자 전환·레거시 제거·운영 적용은 남아 있다. 최신 인계는 `docs/audits/2026-11-04/DEVELOPMENT-HANDOFF-2026-11-04.md`를 참고한다.

작성: 2026-11-01 (Asia/Seoul)

## 현재 제공한 것

`sql/007_atomic_backup.sql`은 별도의 `backup_memberships`, `backup_snapshots`와 읽기/쓰기 RPC를 만든다. 새 경로는 별도 AtomicSyncManager와 등록·복원 화면에 연결되어 있으나 기본 공개 상태는 꺼져 있다. 기존 SyncManager·share/join/pull은 중지 가드로 차단되어 있고 레거시 소스 제거는 남아 있다. 기존 REST 테이블에 저장된 기록을 자동 복사하거나 기존 권한을 자동 승계하지 않는다. 이 SQL만 실행해도 기존 delete→insert, 기존 RLS, 로그인 복원 문제가 해결되는 것은 아니다.

새 테이블은 프로필·성장·접종 전체를 하나의 JSON 스냅샷으로 저장한다. 읽기는 해당 행의 데이터와 버전을 함께 반환하고, 쓰기는 권한 확인과 행 잠금 후 기준 버전이 일치할 때만 전체 행을 바꾼다. 실패하면 그 쓰기 전체가 롤백된다. 사진·메모·발달 관찰은 현재 프로토콜에 포함하지 않는다.

## 적용 전에 필요한 확인

- [ ] 접속 가능한 Supabase 프로젝트와 실제 적용 스키마/마이그레이션 확인
- [ ] 운영과 분리한 스테이징 프로젝트 및 복구 가능한 DB 백업 마련
- [ ] 기존 관리자 인증·레거시 공유 테이블 RLS/직접 쓰기 권한 감사
- [ ] 실제 Auth 사용자와 아기의 관계를 별도 확인해 owner/editor/reader 명단 확정
- [ ] 생성·초대 참여·해제·기록 삭제·계정 탈퇴의 서버 권한/보존 정책 확정

기존 creator_id, creator_email, 기기 ID와 초대코드만으로 새 membership을 자동 등록하지 않는다. 기존 코드에서 쓰일 수 있던 값이므로 소유권을 검증한 자료와 대조해야 한다. 브라우저 사용자는 새 membership 테이블에 자신을 등록할 수 없다.

## 스테이징 적용 순서

1. 기존 버전의 쓰기를 중지하거나 일관된 추출 시점을 확보한다. 이관 도중 레거시 기록이 계속 바뀌면 기준 데이터가 섞일 수 있다.
2. 신뢰할 수 있는 DB 관리자 계정으로 007을 적용한다. 일반 앱 계정으로 실행하지 않는다. 실패하면 SQL 전체 트랜잭션을 롤백하며, 이미 적용한 프로젝트에서 중복 실행하는 스크립트는 아니다.
3. 관리자만 검증한 `baby_id/user_id/role`을 `backup_memberships`에 등록한다. 고객 계정에 테이블 직접 쓰기 권한을 추가하지 않는다.
4. 아기별 기존 데이터를 한 벌의 payload로 변환하고 `validate_backup_payload`를 관리자 트랜잭션에서 실행한다. 실제 백신 차수·의료 내용의 정확성은 별도 검수 대상이다.
5. 검증된 payload를 `backup_snapshots`의 revision 0으로 초기화한다. 최초 쓰기 요청이 빈 데이터로 초기화하게 만들지 않는다. 새 테이블과 기존 레거시 테이블은 자동으로 양방향 동기화되지 않는다.
6. 애플리케이션에서 생성/참여/가져오기/새 기기 복원/자동 백업/관리자 조회 경로를 새 canonical 스냅샷으로 함께 전환한다. 이미 구현한 검증 환경 경로와 남은 관리자·공유·삭제 경로를 함께 검토한다.
7. 기존 직접 쓰기 임시 차단을 유지하며 모든 쓰기 주체를 새 경로로 전환한 뒤 비활성 레거시 코드를 제거한다. 레거시 테이블과 새 테이블을 동시에 서로 다른 원본으로 쓰지 않는다.

## 클라이언트가 지켜야 할 계약

- `readAtomicBackup(sharedBabyId)` 결과를 검증하고 사용자/병합 정책에 따라 수락한 후, 그 스냅샷과 버전을 함께 보관한다. 계정·아기·공유 대상·로컬 변경 이력을 분리한다.
- `writeAtomicBackup(sharedBabyId, expectedRevision, requestId, snapshot)`에 그 기준 버전을 전달한다. 모르는 버전을 0으로 대체하거나 최신 버전만 다시 읽어 로컬 값으로 덮어쓰면 안 된다.
- 불확실한 네트워크 응답 뒤에는 동일한 requestId·기준 버전·내용으로 재시도한다. 마지막 성공 요청의 동일 재시도만 중복 갱신 없이 확인한다. 다른 쓰기가 끼어들었다면 오래된 재시도는 충돌로 처리된다.
- 충돌(40001)이면 자동 덮어쓰기나 자동 최신 버전 재전송을 하지 않고 최신 기록 확인/병합 단계로 이동한다.
- RPC 미설치·초기 데이터 없음·권한 없음·잘못된 응답이면 성공으로 표시하지 않는다. 새 모듈은 기존 delete→insert 방식으로 fallback하지 않는다.
- 성공 시에도 snapshot과 버전을 같이 갱신해야 한다. 세션 변경 후 옛 계정의 버전·요청을 새 계정에 재사용하지 않는다.

## 중단·되돌림 원칙

전환 중 문제가 생기면 쓰기를 중지하고 마지막 확인 버전 및 기기 기록을 보존한다. 새 스냅샷을 삭제하거나 레거시 쓰기로 자동 회귀하지 않는다. 두 저장소의 차이를 확인한 후 복구/재전환한다. 기존 서버 데이터 삭제나 계정 파기는 별도의 검토 대상이다.

## 신규 아기 등록 후속 SQL — 2026-11-02

007 다음에 검증 환경에서 `sql/008_atomic_create_backup.sql`을 적용한다. 새 아기는 `create_backup_snapshot` 한 호출로 로그인 소유자·프로필·최초 스냅샷을 등록한다. 현재 검증 환경 UI는 이 경로를 호출하며 운영에서는 꺼져 있다. 영수증은 현재 버전이 아니므로 생성 후 현재 스냅샷을 읽고 수락해야 한다. 요청 ID와 아기 ID 및 원본 payload는 불확실한 응답 뒤에도 동일하게 재사용한다. 상세 구현·삭제 제약은 `docs/audits/2026-11-02/IMPLEMENTATION-ATOMIC-CREATE-2026-11-02.md`를 참고한다.

## 자동 백업·계정 고정 쓰기 — 2026-11-02

`sql/009_account_bound_backup.sql`을 007 이후 검증 환경에 적용한다. 신규 등록도 포함하면 007 → 008 → 009 순서다. 최신 비교·자동 백업 쓰기는 009 RPC를 사용한다. 자동 백업은 등록 플래그와 별도로 `NEXT_PUBLIC_ATOMIC_AUTOBACKUP_ENABLED=true` 및 아기별 사용자 켜기가 필요하다. 운영에는 아직 적용하지 않았다. 상세 검증/한계는 `docs/audits/2026-11-02/IMPLEMENTATION-ATOMIC-AUTOBACKUP-2026-11-02.md`에 기록했다.

## 계정별 목록·새 기기 복원 — 2026-11-02

`sql/010_list_account_backups.sql`은 007 이후 적용한다. 전체 검증 순서는 007 → 008 → 009 → 010이다. 복원은 기존 아기 교체 대신 새 로컬 아기 추가로 제공하며, 읽은 버전/역할을 보관하고 자동 백업은 꺼짐으로 시작한다. 기기 저장 저널은 관련 저장소 읽기 전에 복구한다. 실제 운영에는 적용하지 않았으며 검증 환경의 등록 플래그만 사용한다. `docs/audits/2026-11-02/IMPLEMENTATION-ACCOUNT-RESTORE-2026-11-02.md`의 한계와 후속 검증을 참고한다.

## 기기 한정 연결 해제·재연결 — 2026-11-04

검증 환경의 새 연결은 로컬 기록과 미확정 요청을 보존하며 해제할 수 있다. 서버 삭제나 가족 권한 철회는 하지 않는다. 같은 백업의 최신 기록과 현재 접근 역할을 읽어 재연결하되 자동 백업은 꺼짐이고, 차이/미확정 요청은 명시적 비교/수락 전 전송하지 않는다. 활성 연결과 detached 이력, transfer outbox, reviewWrites는 이후 아기/계정 삭제 범위에 포함해야 한다. SQL 추가/운영 변경은 없다. 최신 상태는 `docs/audits/2026-11-04/DEVELOPMENT-HANDOFF-2026-11-04.md`를 참고한다.

## 가족 공유·서버 파기·기기 병합 — 2026-11-04

검증 순서는 007 → 008 → 009 → 010 → `011_backup_lifecycle.sql`이다. 011은 기존 생성/읽기/쓰기/목록 RPC에도 계정 삭제 장벽·삭제 아기 재생성 차단·스냅샷 우선 잠금을 적용한다. 새 테이블의 직접 권한을 열지 않는다. 서버 데이터 파기 RPC는 service_role 전용이고, 사용자 확인 RPC와 최근 로그인 확인을 통과한 계정 삭제 API만 호출한다.

스테이징에서만 등록/자동 백업 기존 플래그와 `NEXT_PUBLIC_BACKUP_LIFECYCLE_ENABLED=true`, 서버의 `ATOMIC_BACKUP_LIFECYCLE_ENABLED=true`를 설정한다. 실제 저장소 환경 파일과 운영 플래그는 변경하지 않았다. 계정 삭제는 이 서버 플래그가 없으면 중지된다.

기기 삭제와 서버 삭제는 별도 확인 화면이다. 서버 삭제는 기기 기록을 유지하며, 계정 삭제는 소유 백업을 파기하고 다른 소유자의 백업에서 본인 접근만 제거한다. 공유 초대는 수신 계정 지정·24시간·토큰 해시 저장 방식이다. 현재 아기 병합/교체는 서버 버전 재검사 뒤 기기 저널로 반영하고 자동 백업은 꺼진다.

`npm run check:local-lifecycle`, `npm run check:account-delete`, `npm run check:restore-journal`은 일반 회귀 검사다. `npm run check:lifecycle-stage`는 별도 PostgreSQL이 127.0.0.1:55439에서 실행 중이어야 하며 운영 연결을 받지 않는다. 상세 재현과 실제 검증 한계는 `IMPLEMENTATION-STEPS2-7-2026-11-04.md`에 기록했다.
